Обзор моделей Claude

У Claude три семейства моделей, оптимизированных под разные приоритеты:

Opus — самая «умная» модель для сложных многошаговых задач, требующих глубоких рассуждений и планирования. Компромисс: выше стоимость и задержка.

Sonnet — сбалансированная модель: хороший интеллект, скорость и стоимость. Сильна в программировании и точном редактировании кода. Лучший выбор для большинства практических задач.

Haiku — самая быстрая модель, оптимизированная под скорость и низкую стоимость. Без возможностей рассуждения, как у Opus/Sonnet. Лучше всего подходит для взаимодействия с пользователем в реальном времени и обработки больших объёмов.

Как выбирать: приоритет — интеллект → Opus. Приоритет — скорость → Haiku. Сбалансированные требования → Sonnet.

Частый подход — использовать несколько моделей в одном приложении в зависимости от конкретной задачи, а не выбирать одну.

У всех моделей общие базовые возможности: генерация текста, программирование, анализ изображений. Главное различие — в фокусе оптимизации.

Доступ к API

Доступ к API — процесс из 5 шагов от ввода пользователя до отображения ответа.

Шаг 1: клиент отправляет текст пользователя на сервер разработчика (никогда не обращайтесь к Anthropic API напрямую из клиентских приложений — API-ключ должен оставаться секретным).

Шаг 2: сервер делает запрос к Anthropic API через SDK (Python, TypeScript, JavaScript, Go, Ruby) или обычный HTTP. Обязательные параметры: API-ключ + имя модели + список сообщений + лимит max_tokens.

Шаг 3: генерация текста проходит 4 стадии:

  • Токенизация — разбиение входа на токены (слова / части слов / символы / пробелы)
  • Эмбеддинг — превращение токенов в списки чисел, описывающие все возможные значения слова
  • Контекстуализация — корректировка эмбеддингов с учётом соседних токенов для уточнения смысла
  • Генерация — выходной слой выдаёт вероятности следующего слова, модель выбирает его с учётом вероятности и случайности, добавляет и повторяет процесс

Шаг 4: модель останавливается, когда достигнут max_tokens или сгенерирован специальный токен конца последовательности.

Шаг 5: API возвращает серверу ответ со сгенерированным текстом, счётчиками использования и stop_reason; сервер передаёт его клиенту для отображения.

  • Токен — фрагмент текста (слово / часть слова / символ)
  • Эмбеддинг — числовое представление значений слова
  • Контекстуализация — уточнение смысла по соседним словам
  • max_tokens — ограничение длины генерации
  • stop_reason — причина, по которой модель остановилась

Отправка запроса

Запрос к Anthropic API — это 4 шага подготовки плюс понимание структуры сообщений.

Шаги подготовки:

  1. Установить пакеты: pip install anthropic python-dotenv в Jupyter-ноутбуке
  2. Сохранить API-ключ: создать файл .env с ANTHROPIC_API_KEY="your_key" (исключить из системы контроля версий)
  3. Загрузить переменную окружения: безопасно подгрузить ключ через python-dotenv
  4. Создать клиент: инициализировать клиент anthropic и задать переменную модели (claude-3-sonnet)

Структура запроса:

  • Функция — client.messages.create()
  • Обязательные аргументы — model, max_tokens, messages
  • model — имя используемой модели Claude
  • max_tokens — страховочный лимит длины генерации (а не целевая длина)
  • messages — список реплик разговора

Типы сообщений:

  • Сообщение пользователя — {"role": "user", "content": "ваш текст"} (текст, написанный человеком)
  • Сообщение ассистента — содержит ответы, сгенерированные моделью

Получение ответа:

  • Полный ответ — содержит метаданные и вложенную структуру
  • Только текст — message.content[0].text извлекает сгенерированный текст

Пример: client.messages.create(model=model, max_tokens=1000, messages=[{"role": "user", "content": "What is quantum computing?"}])

Многоходовые диалоги

Многоходовой диалог — разговор из нескольких обменов репликами с сохранением контекста.

Ключевое ограничение: Anthropic API не хранит сообщения. Каждый запрос независим и ничего не «помнит» о предыдущих.

Решение из двух шагов:

  1. Вручную вести список сообщений в коде
  2. Отправлять всю историю разговора с каждым следующим запросом

Структура сообщений — список словарей с полями role (user/assistant) и content.

Ход разговора:

  • Отправить первое сообщение пользователя
  • Получить ответ ассистента
  • Добавить ответ ассистента в историю
  • Добавить новое сообщение пользователя в историю
  • Отправить всю историю, чтобы продолжение учитывало контекст

Нужные вспомогательные функции:

  • add_user_message(messages, text) — добавляет сообщение пользователя в историю
  • add_assistant_message(messages, text) — добавляет ответ ассистента в историю
  • chat(messages) — отправляет историю в API и возвращает ответ

Без истории ответы теряют контекст и связность. С полной историей Claude держит контекст и даёт уместные продолжения.

Системные промпты

Системный промпт — способ настроить стиль и тон ответов Claude, назначив ему определённую роль или модель поведения.

Реализация — передать системный промпт обычной строкой в функцию create через аргумент system.

Назначение — управлять тем, как Claude отвечает, а не тем, что он отвечает. Пример: в роли репетитора по математике Claude даёт подсказки вместо готовых ответов.

Структура — первая строка обычно назначает роль («Ты — терпеливый репетитор по математике»), дальше идут конкретные инструкции по поведению.

Ключевой принцип — системный промпт задаёт подход к ответу, а не содержание. Один и тот же вопрос обрабатывается по-разному в зависимости от роли.

Техническая реализация — собрать словарь params, условно добавить ключ system, если промпт передан, и передать параметры в create через распаковку **. Если промпт None — вообще не передавать параметр system.

Пример использования — репетитор по математике, который даёт наводки и подсказки, а не полные решения, побуждая ученика думать самостоятельно.

Temperature

temperature — параметр (0–1), управляющий случайностью генерации текста через влияние на вероятности выбора токенов.

Процесс генерации: входной текст → токенизация → назначение вероятностей возможным следующим токенам → выбор токена по вероятностям → повтор.

Влияние temperature:

  • Temperature 0 — детерминированный вывод, всегда выбирается самый вероятный токен
  • Более высокая temperature — растёт шанс выбора менее вероятных токенов, вывод креативнее и неожиданнее

Рекомендации:

  • Низкая (около 0) — извлечение данных, фактические задачи, где важна стабильность
  • Высокая (около 1) — творческие задачи: брейншторм, тексты, шутки, маркетинг

Реализация: добавить параметр temperature в вызов API. Высокое значение не гарантирует разные ответы — оно лишь повышает вероятность вариаций.

Суть: temperature напрямую меняет распределение вероятностей следующего токена, делая самые вероятные токены более или менее доминирующими.

Стриминг ответов

Стриминг — показ ответа ИИ по частям по мере генерации вместо ожидания полного ответа.

Какую проблему решает: генерация может занимать 10–30 секунд, а пользователь ждёт мгновенной реакции, а не просто спиннера.

Как работает:

  1. Сервер отправляет сообщение пользователя в Claude
  2. Claude сразу присылает начальный ответ (без текста, просто подтверждение)
  3. Затем идёт поток событий, каждое содержит фрагмент текста
  4. Сервер пересылает фрагменты на фронтенд для отображения в реальном времени

Типы событий:

  • message_start — начальное подтверждение
  • content_block_start — начало генерации текста
  • content_block_delta — сами фрагменты текста (самое важное)
  • content_block_stop / message_stop — генерация завершена

Реализация:

  • Базово: client.messages.create(stream=True) возвращает итератор событий
  • Упрощённо: client.messages.stream() со свойством text_stream отдаёт только текст
  • Итоговое сообщение: stream.get_final_message() собирает все фрагменты для сохранения

Преимущества: лучший UX за счёт мгновенно видимого ответа и полное сообщение для сохранения в базу.

Управление выводом модели

Управление выводом — две ключевые техники помимо правки самого промпта.

Предзаполнение (prefill) сообщения ассистента — ручное добавление сообщения ассистента в конец диалога, чтобы направить ответ.

Как работает:

  • Собрать список сообщений: промпт пользователя + вручную написанное сообщение ассистента
  • Claude воспринимает это сообщение как уже написанное им самим
  • Claude продолжает ответ ровно с конца предзаполненного текста
  • Ответ смещается в заданном направлении

Важно: Claude продолжает с точного места окончания prefill, а не с нового предложения. Prefill и сгенерированный текст нужно склеивать.

Пример: prefill «Кофе лучше, потому что» → Claude продолжает аргументацию в пользу кофе.

Стоп-последовательности — принудительная остановка генерации при появлении заданной строки.

Как работает:

  • Передать строку стоп-последовательности в функцию chat
  • Когда Claude генерирует эту строку, ответ сразу обрывается
  • Сама стоп-последовательность в итоговый вывод не попадает

Пример: промпт «посчитай от 1 до 10» + стоп-последовательность «five» → вывод обрывается на «four, » (five не включается).

Уточнение: стоп-последовательность «, five» → чистый вывод «one, two, three, four».

Обе техники дают точный контроль над направлением и длиной ответа без изменения основного промпта.

Структурированные данные

Генерация структурированных данных — техника, сочетающая prefill сообщения ассистента и стоп-последовательности, чтобы получать «сырой» вывод без пояснительных вступлений и заключений Claude.

Проблема: при генерации JSON/кода/структурированного контента Claude автоматически добавляет markdown-форматирование, заголовки и комментарии. А пользователю часто нужны только данные — чтобы просто скопировать.

Шаблон решения:

  1. Сообщение пользователя — запрос структурированных данных
  2. Prefill ассистента — открывающий разделитель (например, ```json)
  3. Стоп-последовательность — закрывающий разделитель (например, ```)

Как это работает: Claude видит предзаполненное сообщение, считает, что уже начал ответ, генерирует только запрошенный контент и останавливается на разделителе.

Результат — чистые структурированные данные без лишнего форматирования и комментариев.

Применение — работает для любых структурированных данных (JSON, Python-код, списки и т. д.), не только JSON. Используйте всегда, когда нужен чистый, пригодный для парсинга вывод без пояснений.

Главное преимущество — вывод можно сразу использовать или копировать без ручного выделения и парсинга лишнего текста.

Оценка промптов

Промпт-инжиниринг — приёмы написания и редактирования промптов, помогающие Claude понять запрос и желаемый ответ.

Оценка промптов (prompt evaluation) — автоматизированное тестирование промптов по объективным метрикам для измерения их эффективности.

Три пути после написания промпта:

  1. Проверить раз-другой и выкатить в прод (ловушка)
  2. Проверить на своих входных данных и слегка подправить под крайние случаи (ловушка)
  3. Прогнать через пайплайн оценки и получить объективную оценку (рекомендуется)

Вывод: инженеры обычно недотестируют промпты. Используйте пайплайны оценки, чтобы получить объективные баллы до итераций и деплоя.

Типичный процесс оценки

Типичный процесс оценки — итеративный цикл улучшения промпта из 6 шагов.

Шаг 1: написать черновик промпта — базовую версию для оптимизации.

Шаг 2: создать датасет для оценки — набор тестовых входов (от 3 примеров до тысяч; вручную или сгенерированных LLM).

Шаг 3: получить варианты промпта — подставить каждый вход из датасета в шаблон промпта.

Шаг 4: получить ответы LLM — отправить каждый вариант в Claude и собрать результаты.

Шаг 5: оценить ответы — грейдер выставляет балл каждому ответу (например, по шкале 1–10), средний балл показывает общее качество промпта.

Шаг 6: итерировать — изменить промпт по результатам, повторить весь процесс, сравнить версии.

Главное: стандартной методологии нет. Есть много open-source и платных инструментов. Можно начать с простой собственной реализации. Сложность оценивания бывает разной. Объективные баллы позволяют системно улучшать промпт через A/B-сравнение.

Генерация тестовых датасетов

Собственный процесс оценки промпта = собрать промпт + сгенерировать тестовый датасет + оценить качество.

Цель — промпт-помощник по коду для AWS, который выдаёт только Python, JSON-конфиг или регулярное выражение без пояснений.

Способы получить датасет — собрать вручную или сгенерировать с помощью Claude (для генерации лучше брать быстрые модели вроде Haiku).

Структура датасета — массив JSON-объектов со свойством task, описывающим запрос пользователя.

Процесс генерации: попросить Claude придумать тест-кейсы → prefill сообщения ассистента ```json → стоп-последовательность ``` → распарсить ответ как JSON → сохранить в файл.

Ключевая реализация — функция generate_dataset(): отправляет промпт в Claude, получает структурированный JSON с тестовыми задачами и сохраняет его в dataset.json для последующей оценки.

Тестовый датасет позволяет системно оценивать промпт, прогоняя его на множестве сценариев и измеряя стабильность качества.

Запуск оценки

Запуск оценки — объединение тест-кейсов с промптами, прогон через LLM и оценка результатов.

Тест-кейс — отдельная запись из датасета (JSON-объект).

Три основные функции:

  • run_prompt — объединяет тест-кейс с промптом, отправляет в Claude, возвращает вывод
  • run_test_case — вызывает run_prompt, оценивает результат, возвращает словарь-сводку
  • run_eval — проходит по датасету, вызывает run_test_case для каждого кейса, собирает результаты

Базовая структура промпта — «Please solve the following task: [test_case_task]» (стартовая версия v1).

Текущие ограничения — нет инструкций по формату вывода, балл зашит в код (score=10), ответы Claude многословны.

Время выполнения — около 31 секунды на модели Haiku для всего датасета.

Формат результата — массив объектов с выводом Claude, исходным тест-кейсом и баллом.

Следующий шаг — реализовать нормальную систему оценки вместо захардкоженных баллов.

Ядро пайплайна оценки = датасет + промпт + LLM + грейдер, при минимальной сложности кода.

Оценка с помощью модели

Оценка с помощью модели (model-based grading) — система, которая берёт выводы модели и выставляет им объективные баллы (обычно 1–10, где 10 — наивысшее качество).

Три типа грейдеров:

  • Кодовые грейдеры — программные проверки (длина, наличие слов, валидность синтаксиса, читаемость)
  • Модельные грейдеры — дополнительный вызов API для оценки исходного вывода; очень гибкие для оценки качества и следования инструкциям
  • Человеческие грейдеры — ответы оценивает человек; максимально гибко, но долго и утомительно

Ключевые требования: грейдер должен давать объективный сигнал (обычно числовой балл). Критерии оценки нужно определить заранее.

Шаблон реализации модельного грейдера:

  • Написать подробный промпт, запрашивающий сильные стороны / слабые стороны / обоснование / балл (а не только балл — иначе модель склонна ставить средние оценки)
  • Использовать JSON-формат ответа с prefill ассистента и стоп-последовательностями
  • Распарсить JSON, получить балл и обоснование
  • Посчитать средний балл по тест-кейсам как итоговую метрику

Модельные грейдеры очень гибкие, но могут быть непоследовательны. Тем не менее они дают объективную базу для оптимизации промптов.

Оценка с помощью кода

Оценка с помощью кода (code-based grading) — автоматическая валидация выводов LLM, содержащих код, JSON или регулярные выражения.

Базовая реализация:

  • validate_json() — пробует распарсить JSON, возвращает 10 при успехе и 0 при ошибке
  • validate_python() — пробует распарсить AST, возвращает 10 при успехе и 0 при ошибке
  • validate_regex() — пробует скомпилировать regex, возвращает 10 при успехе и 0 при ошибке

Требования к датасету:

  • Должен содержать ключ format с ожидаемым типом вывода (JSON / Python / RegEx)
  • Добавляется через изменение шаблона промпта для автоматической генерации датасета

Промпт:

  • Инструкция модели — отвечать только «сырым» кодом/JSON/regex
  • Без комментариев, пояснений и рассуждений
  • Prefill сообщения ассистента блоком ```code```
  • Стоп-последовательности для извлечения чистого вывода

Система баллов:

  • Итоговый балл = (балл модели + балл синтаксиса) / 2
  • Сочетает смысловую оценку с проверкой синтаксиса
  • Позволяет измерять и корректность, и техническую валидность

Ключевое ограничение — нужно заранее знать ожидаемый формат, чтобы выбрать правильный валидатор.

Промпт-инжиниринг

Промпт-инжиниринг — улучшение промптов ради более надёжного и качественного вывода языковых моделей.

Структура модуля: начать со слабого промпта → пошагово применять техники промпт-инжиниринга → оценивать улучшение после каждой техники → наблюдать рост качества.

Пример задачи: сгенерировать план питания на день для спортсмена по росту, весу, цели и ограничениям в питании.

Техническая подготовка:

  • Обновлённый пайплайн оценки с гибким классом-оценщиком промптов
  • Поддержка конкурентности (настройте max_concurrent_tasks под свои rate limits)
  • Метод generate_dataset() создаёт тест-кейсы с заданными входами
  • Функция run_prompt() обрабатывает каждый тест-кейс отдельно

Ключевые компоненты:

  • prompt_input_spec — словарь, описывающий обязательные входы промпта
  • extra_criteria — дополнительные требования для модельной оценки
  • output.html — отформатированный отчёт с результатами тест-кейсов и баллами

Процесс: написать начальный промпт → подставить входы тест-кейсов → запустить оценку → применить техники → оценить заново → повторять до приемлемого качества.

Начальные результаты: с простым промптом ожидайте низкие баллы (например, 2.32), особенно на менее мощных моделях. По мере применения техник баллы растут.

Ясность и прямота

Ясность и прямота — используйте простой, прямой язык и глагол действия в первой строке промпта, чтобы точно обозначить задачу.

Важность первой строки — это самая критичная часть промпта, задающая основу ответа ИИ.

Структура = глагол действия + чёткое описание задачи + требования к выводу.

Примеры:

  • «Напиши три абзаца о том, как работают солнечные панели»
  • «Назови три страны, использующие геотермальную энергию, и для каждой приведи статистику выработки»
  • «Составь план питания на день для спортсмена с учётом его ограничений в питании»

Ключевые элементы = глагол действия в начале + прямая формулировка задачи + детали ожидаемого результата.

Результат — рост качества промпта (в примере балл вырос с 2.32 до 3.92).

Конкретность

Конкретность — добавление рекомендаций или шагов, направляющих вывод модели в нужную сторону.

Два типа рекомендаций:

  • Тип A (атрибуты) — перечислить желаемые качества результата (длина, структура, формат)
  • Тип B (шаги) — задать конкретные шаги рассуждения для модели

Тип A управляет характеристиками вывода. Тип B — тем, как модель приходит к ответу.

В профессиональных промптах их часто комбинируют.

Когда использовать:

  • Тип A (атрибуты) — рекомендуется почти для всех промптов
  • Тип B (шаги) — для сложных задач, где нужно, чтобы модель учла более широкий контекст или точки зрения, о которых сама бы не подумала

Пример: балл промпта с планом питания вырос с 3.92 до 7.86 после добавления рекомендаций — конкретность заметно повышает качество.

Структура с помощью XML-тегов

XML-теги для структуры промпта — использование XML-тегов для организации и разграничения разных частей контента в промпте, чтобы модель лучше его понимала.

Зачем — когда в промпт подставляется много контента, XML-теги помогают модели различать типы информации и понимать, какой текст к чему относится.

Реализация — оборачивать части контента в описательные теги, например <sales_records></sales_records> или <my_code></my_code>, вместо того чтобы сваливать всё неструктурированным текстом.

Именование тегов — используйте описательные конкретные имена (sales_records лучше, чем data), чтобы передать смысл содержимого.

Пример — промпт для отладки, где смешаны код и документация, становится понятнее при разделении на теги <my_code> и <docs>.

Преимущества — структура промпта очевидна модели, меньше путаницы с границами контента, выше качество вывода даже для небольших блоков.

Применение — можно оборачивать любой подставляемый контент, например <athlete_information>, даже короткий, чтобы показать, что это внешние данные, которые нужно учесть.

Примеры в промпте

One-shot / multi-shot промптинг — добавление примеров в промпт, чтобы направить поведение модели. One-shot — один пример, multi-shot — несколько.

Реализация: оформлять примеры в XML-тегах с образцом входа и идеальным выходом. Всегда чётко оборачивайте примеры, чтобы отделить их от основного промпта.

Основные применения:

  • Обработка крайних случаев (распознавание сарказма, пограничные сценарии)
  • Сложное форматирование вывода (JSON-структуры, особые форматы)
  • Уточнение ожидаемого качества и стиля ответа

Лучшие практики:

  • Добавлять контекст для крайних случаев («особенно внимательно отнесись к сарказму»)
  • Объяснять, почему этот вывод идеален
  • Брать в качестве образцов лучшие по баллам примеры из оценки промптов
  • Размещать примеры после основных инструкций и рекомендаций

Усиление эффекта: сочетайте примеры с объяснением, что делает их идеальными, — это закрепляет нужные характеристики вывода.

Знакомство с инструментами (Tool Use)

Tool use — способ дать Claude доступ к внешней информации за пределами обучающих данных.

Ограничение по умолчанию: Claude знает только то, что было в обучающих данных, и не владеет актуальной информацией в реальном времени.

Процесс работы с инструментами:

  1. Отправить в Claude исходный запрос + инструкции, как получать внешние данные
  2. Claude решает, нужны ли внешние данные, и запрашивает конкретную информацию
  3. Сервер выполняет код и получает данные из внешних источников
  4. Отправить в Claude повторный запрос с полученными данными
  5. Claude формирует итоговый ответ на основе исходного промпта и внешних данных

Пример с погодой: пользователь спрашивает текущую погоду → Claude запрашивает данные о погоде → сервер вызывает погодный API → Claude получает данные → Claude даёт ответ с учётом этих данных.

Суть: инструменты позволяют дополнять ответы Claude актуальной информацией, организуя получение внешних данных между запросами к Claude.

Обзор проекта

Цель — научить Claude ставить напоминания по времени с помощью инструментов в Jupyter-ноутбуке.

Целевое взаимодействие: пользователь — «Поставь напоминание о приёме у врача через неделю после четверга» → Claude — «Я напомню вам в это время».

Три ключевые проблемы, требующие инструментов:

  1. Нет знания о времени — Claude знает текущую дату, но не точное время
  2. Ошибки в вычислениях со временем — Claude иногда ошибается при сложении дат (например, 379 дней от 13 января 1973 года)
  3. Нет механизма напоминаний — Claude понимает концепцию напоминания, но не может её реализовать

Три соответствующих инструмента:

  1. Инструмент текущей даты и времени — получает текущие дату и время
  2. Инструмент прибавления длительности — прибавляет промежуток к дате (например, текущая дата + 20 дней)
  3. Инструмент установки напоминания — собственно ставит напоминание

Подход — по одному инструменту за раз, постепенно приходя к координации нескольких инструментов.

Функции-инструменты

Функции-инструменты — Python-функции, которые выполняются автоматически, когда Claude нужна дополнительная информация, чтобы помочь пользователю.

Ключевые характеристики:

  • Обычные Python-функции, которые вызываются, когда Claude решает, что нужны дополнительные данные
  • Должны иметь описательные имена функций и аргументов
  • Должны валидировать вход и выбрасывать ошибки с понятными сообщениями
  • Сообщения об ошибках видны Claude, и он может повторить вызов с исправленными параметрами

Лучшие практики:

  1. Хорошие имена функций и аргументов
  2. Валидация входа с немедленным выбросом ошибки при некорректных данных
  3. Понятные сообщения об ошибках, подсказывающие, как исправить

Пример реализации:

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
    if not date_format:
        raise ValueError("date_format cannot be empty")
    return datetime.now().strftime(date_format)

Порядок работы: Claude понимает, что нужна информация → вызывает функцию-инструмент → получает результат или ошибку → при ошибке может повторить с исправлениями.

Назначение: расширить возможности Claude за пределы обучающих данных, дав доступ к информации в реальном времени — текущему времени, погоде и т. п.

Схемы инструментов

Схемы инструментов — спецификации в формате JSON Schema, описывающие функции-инструменты и их параметры для языковой модели.

JSON Schema — спецификация валидации данных (не специфичная для ML), которую ML-сообщество переняло для вызова инструментов.

Структура схемы инструмента:

  • name — идентификатор инструмента
  • description — 3–4 предложения: что делает инструмент, когда его использовать, какие данные он возвращает
  • input_schema — сама JSON Schema с описанием аргументов функции, их типов и описаний

Лайфхак для генерации схемы:

  1. Отнести функцию-инструмент в Claude.ai
  2. Промпт: «write valid JSON schema spec for tool calling for this function, follow best practices in attached documentation»
  3. Приложить страницу документации Anthropic API про tool use
  4. Скопировать сгенерированную схему

Шаблон реализации:

  • Давать функциям описательные имена
  • Называть схемы [имя_функции]_schema
  • Импортировать ToolParam из anthropic.types
  • Оборачивать словарь схемы в ToolParam(), чтобы избежать ошибок типов

Назначение — сообщить Claude, какие инструменты доступны, какие аргументы нужны и в каком контексте их использовать, через стандартный формат JSON-валидации.

Работа с блоками сообщений

Запросы к Claude с инструментами

Шаг 3: запрос к Claude с инструментами — передать схемы инструментов вместе с сообщением пользователя через аргумент tools, содержащий JSON Schema-спецификации.

Сообщения из нескольких блоков

Меняется структура контента — сообщения теперь состоят из нескольких блоков, а не только из текстового.

Формат ответа с инструментом — сообщение ассистента содержит:

  • Текстовый блок — пояснение для пользователя
  • Блок tool use — имя функции и аргументы для выполнения инструмента

Управление историей сообщений

Критичное требование — вести историю разговора вручную, поскольку Claude ничего не хранит.

Работа с несколькими блоками — добавлять в список сообщений весь response.content (все блоки), а не только текст.

Нужно обновить вспомогательные функции — add_user_message и add_assistant_message должны поддерживать несколько блоков, а не только один текстовый.

Ход разговора: сообщение пользователя → ответ ассистента с блоком tool use → выполнение инструмента → ответ Claude со всей историей.

Отправка результатов инструментов

Результаты инструментов — результаты выполненных функций, которые отправляются обратно в Claude в следующем запросе.

Процесс: выполнить запрошенную Claude функцию → создать блок tool result → отправить повторный запрос со всей историей разговора.

Структура блока tool result:

  • tool_use_id — совпадает с ID исходного блока tool use, чтобы связать запрос с результатом
  • content — вывод функции, приведённый к строке (обычно JSON)
  • is_error — булев флаг ошибки выполнения (по умолчанию false)

Зачем нужен tool use ID — связывать несколько запросов инструментов с правильными результатами, когда Claude вызывает инструменты одновременно. У каждого вызова свой ID, и результат должен ссылаться на соответствующий ID.

Требования к повторному запросу:

  • Включить полную историю (исходное сообщение пользователя + сообщение ассистента с tool use + новое сообщение пользователя с результатом)
  • Обязательно передать исходные схемы инструментов, даже если они больше не понадобятся
  • Блок tool result помещается в сообщение пользователя, а не ассистента

Ход разговора: запрос пользователя → ответ ассистента (текст + блоки tool use) → сервер выполняет инструмент → сообщение пользователя с блоком tool result → итоговый ответ Claude с учётом результатов.

Многоходовые диалоги с инструментами

Многоходовые диалоги с инструментами — разговоры, где Claude последовательно использует несколько инструментов, чтобы ответить на один запрос.

Цепочка вызовов: пользователь задаёт вопрос → Claude запрашивает первый инструмент → он выполняется → результат возвращается → Claude запрашивает второй инструмент → он выполняется → результат возвращается → Claude даёт итоговый ответ.

Пример: пользователь спрашивает «какой день будет через 103 дня?» → Claude вызывает get_current_datetime → затем add_duration_to_datetime → даёт ответ.

Шаблон реализации — цикл while, который вызывает Claude, пока тот запрашивает инструменты, проверяя каждый ответ на наличие блоков tool_use.

Функция run_conversation — принимает начальные сообщения, в цикле вызывает Claude, выполняет запрошенные инструменты, добавляет результаты в разговор и продолжает до финального ответа.

Нужный рефакторинг:

  • add_user_message / add_assistant_message — поддержка нескольких блоков вместо простого текста
  • Функция chat — принимает параметр tools и возвращает всё сообщение, а не только первый текстовый блок
  • Помощник text_from_message — извлекает все текстовые блоки из сообщения с несколькими блоками

Ключевая мысль — невозможно заранее знать, сколько инструментов понадобится для запроса, поэтому система должна автоматически обрабатывать цепочки вызовов любой длины.

Реализация нескольких ходов

Реализация нескольких ходов — вызывать Claude до тех пор, пока он не перестанет запрашивать инструменты.

Поле stop_reason показывает, почему Claude остановил генерацию:

  • stop_reason = "tool_use" — Claude хочет вызвать инструмент
  • Есть и другие значения, но чаще всего проверяют именно tool_use

Функция run_conversation — основной цикл:

  1. Вызывает Claude с сообщениями и доступными инструментами
  2. Добавляет ответ ассистента в историю
  3. Проверяет stop_reason: если не tool_use — выход из цикла
  4. Если tool_use — вызывает run_tools
  5. Добавляет результаты инструментов как сообщение пользователя
  6. Повторяет, пока запросы инструментов не закончатся

Функция run_tools обрабатывает несколько блоков tool use:

  1. Отбирает из message.content блоки с type="tool_use"
  2. Перебирает каждый запрос инструмента
  3. Выполняет нужную функцию через помощник run_tool
  4. Создаёт блоки tool result: type="tool_result", tool_use_id = исходный ID, content = вывод в JSON, is_error = булево
  5. Возвращает список всех блоков tool result

Функция run_tool — диспетчер:

  • Принимает tool_name и tool_input
  • Через условия сопоставляет имя инструмента с функцией
  • Выполняет нужную функцию
  • Легко масштабируется на много инструментов

Обработка ошибок — try/except вокруг выполнения инструмента:

  • Успех: is_error=false, content = вывод инструмента
  • Ошибка: is_error=true, content = текст ошибки

Ключевые моменты архитектуры:

  • Сообщение ассистента может содержать несколько блоков (текст + несколько tool use)
  • На каждый блок tool use — отдельный tool result
  • Все результаты отправляются одним сообщением пользователя
  • Процесс повторяется, пока Claude не даст финальный ответ только текстом

Использование нескольких инструментов

Добавление нескольких инструментов — подключение новых инструментов к уже готовой системе после первоначальной настройки каркаса.

Процесс из 3 шагов: (1) добавить схемы инструментов в список tools функции RunConversation, (2) добавить условия в функцию RunTool для новых имён инструментов, (3) реализовать сами функции.

Ключевые компоненты:

  • Функция RunConversation — содержит список инструментов, о которых знает Claude
  • Функция RunTool — направляет вызовы в нужные функции по имени инструмента
  • Схемы инструментов — описывают структуру инструмента для модели
  • Функции-инструменты — собственно код реализации

Добавленные инструменты:

  • AddDurationToDateTime — вычисляет дату/время со смещением
  • SetReminder — создаёт напоминание (заглушка, которая печатает подтверждение)

Цепочки инструментов — ИИ может последовательно использовать несколько инструментов в одном диалоге (например, сначала вычислить дату, потом поставить напоминание на неё).

Структура сообщений — ответ ассистента может содержать несколько блоков: текст + блоки tool use в одном сообщении.

Масштабируемость — после настройки каркаса добавление инструмента сводится к простому шаблону: схема + маршрутизация + реализация.

Batch-инструмент

Batch-инструмент — инструмент, позволяющий Claude запускать несколько инструментов параллельно в одном сообщении ассистента вместо отдельных последовательных запросов.

Проблема: технически Claude может отправить несколько блоков tool use в одном сообщении, но на практике делает это редко — отсюда лишние последовательные вызовы.

Решение: создать схему batch-инструмента, принимающую список вызовов (invocations), каждый с именем инструмента и аргументами. Вместо прямых вызовов Claude вызывает batch-инструмент с массивом нужных выполнений.

Реализация:

  • Добавить batch-инструмент в схемы с параметром invocations
  • Создать функцию run_batch, перебирающую список вызовов
  • Извлекать имя инструмента и аргументы (распарсенные из JSON) для каждого вызова
  • Вызывать run_tool для каждого запрошенного инструмента
  • Возвращать список batch_output с результатами всех выполнений

Механизм: «подталкивает» Claude к параллельному выполнению через абстракцию более высокого уровня, вручную делая то, что сделали бы несколько блоков tool use.

Результат: один цикл запрос–ответ вместо нескольких последовательных раундов для задач, которые можно выполнять параллельно.

Инструменты для структурированных данных

Инструменты для структурированных данных — альтернативный способ получать структурированный JSON из источников данных через систему инструментов Claude вместо prefill и стоп-последовательностей.

Отличия от подхода через промпт:

  • Более надёжный вывод
  • Более сложная настройка
  • Требуется JSON Schema

Основной процесс:

  1. Описать JSON Schema инструмента, где входные параметры = нужная структура данных
  2. Отправить промпт + схему в Claude
  3. Claude вызывает инструмент со структурированными аргументами по схеме
  4. Извлечь JSON из блока tool use (tool result не нужен)

Критичное требование — принудительный вызов инструмента через параметр tool_choice:

  • tool_choice = {"type": "tool", "name": "your_tool_name"}
  • Гарантирует, что Claude всегда вызовет указанный инструмент

Шаги реализации:

  1. Создать схему инструмента для извлечения
  2. Добавить в функцию chat параметр tool_choice
  3. Передать tool_choice в client.messages.create()
  4. Взять данные из response.content[0].input

Когда использовать — когда надёжность важнее простоты. Подход через промпт хорош для быстрых и простых извлечений, инструменты — для сложных и надёжных.

Инструмент редактирования текста

Text Editor Tool — встроенный инструмент Claude для операций с файлами и текстом (чтение, запись, создание, замена, отмена изменений для файлов и директорий).

Ключевые особенности:

  • В Claude встроена только JSON-схема, реализацию нужно писать самому
  • Отправленная в Claude «заглушка» схемы автоматически разворачивается в полную схему
  • Строка типа схемы зависит от версии модели (у 3.5 и 3.7 разные даты)
  • Позволяет Claude «из коробки» работать как программист

Что нужно реализовать:

  • Свой класс/функции для обработки запросов Claude к инструменту
  • Функции для просмотра файлов, замены строк, создания файлов и т. д.
  • Реальные операции с файловой системой Claude не выполняет

Процесс:

  1. Отправить в Claude минимальную заглушку схемы (имя + тип с датой версии)
  2. Claude внутренне разворачивает её в полную схему
  3. Claude присылает запросы tool use
  4. Ваша реализация выполняет реальные операции с файлами
  5. Результаты отправляются обратно в Claude

Сценарии использования:

  • Воспроизвести функциональность ИИ-редактора кода
  • Операции с файлами там, где нет нативных редакторов
  • Автоматическая генерация и рефакторинг кода
  • Работа с проектами из многих файлов

Преимущество — приближает возможности продвинутого редактора кода через вызовы API, а не через GUI.

Инструмент веб-поиска

Web Search Tool — встроенный инструмент Claude для поиска в интернете актуальной или специализированной информации по вопросу пользователя.

Реализация — свой код не нужен, Claude выполняет поиск автоматически.

Требования к схеме:

  • type: "web_search_20250305"
  • name: "web_search"
  • max_uses — число (ограничивает количество поисков, по умолчанию 5)
  • allowed_domains — необязательный список доменов для ограничения поиска

Структура ответа:

  • Текстовые блоки — пояснения Claude
  • Блоки tool use — поисковые запросы, которые выполнил Claude
  • Блоки результатов веб-поиска — найденные страницы (заголовок, URL)
  • Блоки цитат — конкретный текст, подтверждающий утверждения Claude

Ключевые возможности:

  • Несколько поисков за запрос (до лимита max_uses)
  • Ограничение по доменам для контроля качества
  • Система цитирования связывает утверждения с источниками

Отображение в UI:

  • Текстовые блоки — как обычный текст
  • Результаты поиска — списком источников
  • Цитаты — с указанием источника (домен, заголовок, URL, цитируемый текст)

Пример: ограничение поиска доменом NIH.gov для медицинских советов и советов по упражнениям гарантирует научно обоснованную информацию вместо случайного веб-контента.

Знакомство с RAG

RAG (Retrieval Augmented Generation, генерация с дополнением извлечёнными данными) — техника работы с большими документами с помощью языковых моделей.

Проблема: как извлечь конкретную информацию из большого документа (100–1000+ страниц) с помощью Claude, не упираясь в лимиты контекста.

Вариант 1 (напрямую): вставить весь текст документа в промпт.

  • Ограничения: жёсткие лимиты токенов, снижение качества на длинных промптах, выше стоимость, медленнее обработка

Вариант 2 (RAG): процесс из двух шагов

  • Шаг 1: разбить документ на небольшие фрагменты (чанки)
  • Шаг 2: для вопроса пользователя найти самые релевантные чанки и включить в промпт только их

Плюсы RAG: модель фокусируется на релевантном, масштабируется на большие и многочисленные документы, промпты меньше, дешевле, быстрее.

Минусы RAG: сложнее, требует предобработки, нужен механизм поиска релевантных чанков, нет гарантии, что чанки содержат весь нужный контекст, есть много стратегий разбиения (на равные части, по заголовкам).

Главная сложность: определить, что такое релевантность, и выбрать оптимальную стратегию разбиения под задачу.

RAG жертвует простотой ради масштабируемости и эффективности, но требует аккуратной реализации и оценки.

Стратегии разбиения текста

Стратегии разбиения (чанкинга) — способы делить документы на небольшие части для RAG-пайплайнов.

Ключевая проблема: качество разбиения напрямую влияет на качество RAG. Плохое разбиение приводит к извлечению нерелевантного контекста (например, медицинский текст про «bug» находится по запросу о багах в программировании).

Три основные стратегии:

1. Разбиение по размеру — деление текста на строки равной длины

  • Плюсы: просто реализовать, чаще всего используется в продакшене
  • Минусы: обрезанные слова, нехватка контекста
  • Решение: перекрытие (overlap) — включать символы из соседних чанков, чтобы сохранить контекст
  • Компромисс: появляется дублирование текста, но чанки становятся осмысленнее

2. Разбиение по структуре — деление по структуре документа (заголовки, абзацы, разделы)

  • Лучше всего для структурированных документов (markdown, HTML)
  • Ограничение: нужна гарантированная разметка документа
  • Пример: разбить по markdown-заголовкам (##) на чанки-разделы

3. Семантическое разбиение — группировка связанных предложений/разделов с помощью NLP

  • Самая продвинутая техника
  • Объединяет идущие подряд предложения по смысловой близости
  • Сложная реализация

Практические замечания:

  • По символам — самый надёжный запасной вариант, работает с любым документом
  • По предложениям — хорошая середина, если предложения определяются надёжно
  • По разделам — лучший результат, но нужен структурированный вход
  • Выбор стратегии зависит от гарантий формата документа и задачи

Правило: универсально лучшего способа нет — всё зависит от структуры документов и конкретного сценария.

Текстовые эмбеддинги

Текстовые эмбеддинги — числовое представление смысла текста, генерируемое эмбеддинг-моделью.

Эмбеддинг-модель — принимает текст, выдаёт длинный список чисел (в диапазоне от −1 до +1).

Числа эмбеддинга — оценки неизвестных качеств/признаков текста. Теоретически каждое число оценивает отдельный аспект (позитивность, тематика и т. д.), но реальный смысл пользователю неизвестен.

Семантический поиск — использует эмбеддинги, чтобы находить в RAG-пайплайне чанки, связанные с вопросом пользователя. Решает задачу сопоставления запросов с релевантными фрагментами документа.

Процесс RAG-пайплайна: извлечь чанки → пользователь отправляет запрос → найти связанные чанки семантическим поиском → добавить их в промпт как контекст.

Реализация — Anthropic рекомендует Voyage AI для генерации эмбеддингов. Нужен отдельный аккаунт и API-ключ. Бесплатный старт, простая интеграция через SDK.

Суть — эмбеддинги дают сопоставление по смыслу, а не по ключевым словам, что улучшает понимание связей между текстами при поиске.

Полный RAG-процесс

RAG-процесс — 7 шагов, объединяющих разбиение текста, эмбеддинги и векторный поиск для извлечения релевантного контекста к запросу LLM.

  1. Разбиение текста — разделить исходные документы на отдельные фрагменты
  2. Генерация эмбеддингов — превратить чанки в числовые векторы с помощью эмбеддинг-модели
  3. Нормализация — привести длину векторов к 1.0 (эмбеддинг-API делают это автоматически)
  4. Хранение в векторной БД — сохранить эмбеддинги в специальной базе, оптимизированной под операции с векторами
  5. Обработка запроса — превратить вопрос пользователя в эмбеддинг той же моделью
  6. Поиск по сходству — найти наиболее похожие сохранённые эмбеддинги через косинусное сходство
  7. Сборка промпта — объединить вопрос пользователя с найденными чанками и отправить в LLM

Ключевая математика:

  • Косинусное сходство — косинус угла между векторами, значения от −1 до 1; ближе к 1 — больше сходство
  • Косинусное расстояние — 1 минус косинусное сходство; ближе к 0 — больше сходство
  • Векторная БД — выполняет расчёты сходства, чтобы найти ближайшие эмбеддинги

Порядок: предобработка (шаги 1–4) → запрос пользователя → извлечение в реальном времени (шаги 5–7) → ответ LLM.

Реализация RAG-процесса

Реализация RAG — практический разбор процесса из 5 шагов.

Шаг 1: разбиение текста — разделить документ на разделы функцией chunk_by_section для файла report.md.

Шаг 2: генерация эмбеддингов — получить векторы для каждого чанка функцией generate_embedding (принимает строку или список строк).

Шаг 3: наполнение векторного хранилища — создать экземпляр vector index, пройтись по парам чанк–эмбеддинг через zip() и сохранить каждую пару через store.add_vector(embedding, {"content": chunk}). Исходный текст хранится вместе с эмбеддингом, чтобы результаты поиска были осмысленными.

Шаг 4: обработка запроса — пользователь спрашивает «чем занимался отдел разработки ПО в прошлом году», для запроса генерируется эмбеддинг.

Шаг 5: поиск по сходству — store.search(user_embedding, 2) находит 2 самых релевантных чанка и возвращает их с косинусными расстояниями (0.71 для второго раздела, 0.72 для раздела о методологии).

Ключевые компоненты:

  • Класс Vector Index — собственная реализация векторной БД
  • Косинусное расстояние — метрика сходства между запросом и сохранёнными эмбеддингами
  • Хранение метаданных — исходный текст рядом с эмбеддингом делает результаты поиска полезными

Процесс работает, но имеет ограничения, требующие доработки.

Лексический поиск BM25

BM25 (Best Match 25) — алгоритм лексического поиска, который часто используют в RAG-пайплайнах в дополнение к семантическому поиску.

Проблема чисто семантического поиска — он может пропускать точные совпадения терминов и возвращать нерелевантные результаты, даже если нужные термины часто встречаются в определённых документах.

Гибридный поиск — семантический поиск (эмбеддинги/векторная БД) и лексический (BM25) запускаются параллельно, а результаты объединяются для лучшего баланса.

Шаги алгоритма BM25:

  1. Токенизировать запрос на отдельные термины (убрать пунктуацию, разбить по пробелам)
  2. Посчитать частоту каждого термина во всех чанках/документах
  3. Присвоить терминам вес по частоте использования (редкие — важнее, частые вроде «a» — менее важны)
  4. Ранжировать чанки по тому, как часто в них встречаются термины с высоким весом

Суть — термины, часто встречающиеся во всём корпусе, менее важны для релевантности, чем редкие и специфичные.

Преимущества BM25 — лучше находит точные совпадения, выдвигает документы с редкими специфичными терминами, компенсирует слабости семантического поиска.

Реализация — у обеих систем поиска похожий API (функции add_document, search), поэтому их легко комбинировать.

Следующий шаг — объединить результаты обеих систем, получив и понимание смысла, и точное совпадение терминов.

RAG-пайплайн с несколькими индексами

Мультииндексный RAG-пайплайн — система, сочетающая семантический поиск (векторный индекс) и лексический (индекс BM25) для более точного извлечения.

Ключевые компоненты:

  • Векторный индекс — семантический поиск по сходству эмбеддингов
  • Индекс BM25 — лексический поиск по ключевым словам
  • Класс Retriever — обёртка, отправляющая запросы в оба индекса и объединяющая результаты

Reciprocal Rank Fusion (RRF) — техника объединения результатов разных индексов. Формула: RRF_score = сумма 1/(rank + 1) по всем методам поиска для каждого документа. Документы сортируются по наибольшему суммарному баллу.

Пример: векторный поиск вернул [doc2, doc7, doc6], BM25 — [doc6, doc2, doc7]. После RRF итоговый порядок — [doc2, doc6, doc7], потому что doc2 высоко в обоих методах.

Преимущества:

  • Выше точность за счёт сочетания разных парадигм поиска
  • Модульный дизайн со стандартным API (методы search() и add_document())
  • Легко добавить новые индексы
  • Лучше обрабатываются случаи, где один метод не справляется

Такой подход позволяет нескольким методам поиска работать вместе, сохраняя отдельные изолированные классы индексов.

Переранжирование результатов

Переранжирование (reranking) — шаг постобработки, на котором LLM переупорядочивает результаты поиска по релевантности после первичного извлечения.

Процесс: векторный поиск + BM25 → объединение результатов → передать в LLM с просьбой отсортировать документы по релевантности → получить новый порядок.

Детали реализации: для эффективности использовать ID документов вместо полного текста. LLM получает запрос пользователя + документы-кандидаты + инструкцию вернуть самые релевантные в порядке убывания. Prefill ассистента + стоп-последовательность обеспечивают структурированный JSON-вывод.

Компромиссы: точность поиска растёт за счёт понимания LLM смысловой релевантности, но растёт и задержка из-за дополнительного вызова LLM. Особенно полезно, когда первичные методы упускают нюансы запроса (например, «ENG team» и «engineering team»).

Пример: по запросу «Что сделала инженерная команда с инцидентом 2023 года?» после переранжирования раздел о разработке ПО правильно оказался выше раздела о кибербезопасности, хотя гибридный поиск изначально ставил его ниже.

Контекстное извлечение

Contextual Retrieval — техника повышения точности RAG за счёт добавления контекста к чанкам перед созданием эмбеддингов.

Проблема: при разбиении документа отдельные чанки теряют контекст исходного документа, и точность поиска падает.

Решение: шаг предобработки, добавляющий к каждому чанку контекстную информацию до загрузки в базу ретривера.

Процесс:

  1. Взять отдельный чанк + исходный документ
  2. Отправить в LLM (Claude) с просьбой сгенерировать поясняющий контекст
  3. LLM пишет краткий контекст о том, как чанк связан с документом в целом
  4. Объединить контекст с исходным чанком = «контекстуализированный чанк»
  5. Использовать его как вход для векторного индекса и BM25

Работа с большими документами: если документ не помещается в один промпт, использовать выборочный контекст:

  • Включить начальные чанки (1–3) из начала документа — для резюме/аннотации
  • Включить чанки непосредственно перед целевым — для локального контекста
  • Пропустить средние чанки, которые дают менее релевантный контекст

Реализация: функция add_context принимает чанк + исходный текст, генерирует контекст через LLM, склеивает его с чанком и возвращает контекстуализированную версию.

Преимущество: чанки сохраняют связь со структурой документа и перекрёстными ссылками, что повышает точность поиска в сложных документах со взаимосвязанными разделами.

Расширенное мышление (Extended Thinking)

Extended Thinking — возможность Claude подумать перед формированием итогового ответа.

Ключевая механика:

  • Показывает отдельный процесс рассуждений, видимый пользователю
  • Повышает точность на сложных задачах, но добавляет стоимость (токены мышления оплачиваются) и задержку
  • Бюджет мышления — минимум 1024 токена на фазу размышлений
  • max_tokens должен превышать бюджет мышления (например, при бюджете 1024 нужно max_tokens ≥ 1025)

Когда использовать:

  • Включать, когда оптимизация промпта не даёт нужной точности
  • Решать о необходимости по результатам оценки промптов

Структура ответа:

  • Блок thinking — текст рассуждений + криптографическая подпись
  • Текстовый блок — итоговый ответ
  • Подпись — защищает текст рассуждений от подмены (мера безопасности)

Особые случаи:

  • Блоки redacted thinking — зашифрованный текст рассуждений, помеченный системами безопасности
  • Передаются, чтобы сохранить непрерывность диалога без потери контекста
  • Можно принудительно вызвать redacted-блоки тестовой строкой: «entropic magic string triggered redacted thinking [special characters]»

Реализация:

  • Включить thinking и задать параметр бюджета мышления
  • Убедиться, что max_tokens больше бюджета мышления, чтобы хватило места на ответ

Работа с изображениями

Зрение Claude — способность обрабатывать изображения в сообщениях пользователя для анализа, сравнения, подсчёта и описания.

Ограничения:

  • Не более 100 изображений на запрос
  • Есть ограничения по размеру и разрешению
  • Изображения расходуют токены (считаются по высоте и ширине в пикселях)

Блок изображения — специальный тип блока в сообщении пользователя, содержащий либо сырые данные (base64), либо URL изображения в интернете. В одном сообщении может быть несколько таких блоков.

Критический фактор успеха — сильный промптинг. Простые промпты часто не срабатывают.

Техники промптинга для изображений:

  • Пошаговые инструкции по анализу
  • One-shot / multi-shot примеры (чередование пар изображение–текст)
  • Чёткие рекомендации и шаги проверки
  • Структурированные схемы анализа

Пример — автоматическая оценка пожарного риска по спутниковым снимкам: анализ плотности деревьев, подъезда к участку, свеса крыши и выставление числового балла риска.

Реализация — закодировать изображение в base64, создать сообщение с блоком изображения (type: image, source: base64, media_type, data), за которым идёт текстовый блок с подробными инструкциями.

Главный вывод — точность работы с изображениями определяется качеством промпта, а не только качеством картинки.

Работа с PDF

Claude умеет читать PDF напрямую — код почти такой же, как для изображений.

Ключевые отличия в реализации:

  • Тип блока — "document" вместо "image"
  • Media type — "application/pdf" вместо "image/png"
  • Имя переменной — file_bytes вместо image_bytes

Возможности с PDF — извлечение текста, изображений, графиков, таблиц и смешанного контента.

Обработка PDF — универсальное решение для комплексного анализа документов.

Шаблон использования — как с изображениями, но с параметрами для документов.

Цитаты (Citations)

Citations — возможность Claude ссылаться на исходные документы и показывать, откуда взята информация.

Типы цитат:

  • citation_page_location — для PDF: индекс документа, заголовок, начальная и конечная страница, цитируемый текст
  • citation_char_location — для обычного текста: позиция символов в текстовом блоке

Реализация:

  • Добавить в запрос "citations": {"enabled": true}
  • Добавить поле "title" для идентификации документа
  • Работает и с PDF, и с обычным текстом

Структура ответа — контент становится списком текстовых блоков, часть из которых содержит массивы citations с данными о расположении.

Назначение — прозрачность: пользователь может проверить источники и правильность интерпретации.

Польза для UI — всплывающие подсказки с источником, номерами страниц и точным цитируемым текстом при наведении на ссылку.

Ключевой сценарий — дать пользователю разобраться, как Claude строит ответ на основе источников, а не создавать впечатление, что он говорит «по памяти».

Кэширование промптов

Prompt Caching — функция, ускоряющая ответы Claude и снижающая стоимость генерации за счёт переиспользования вычислений из предыдущих запросов.

Обычный запрос: пользователь отправляет сообщение → Claude обрабатывает вход (строит внутренние структуры данных, выполняет вычисления) → генерирует вывод → выбрасывает всю проделанную работу → готов к следующему запросу.

Проблема: если следующие запросы содержат те же входные сообщения, Claude приходится заново делать ту же работу, которую он только что выбросил.

Решение: кэширование сохраняет результаты обработки входа во временный кэш. Когда тот же вход приходит снова, Claude берёт готовую работу из кэша, что резко ускоряет ответ.

Главная польза: переиспользование вычислений вместо повторной обработки одинакового контента.

Правила кэширования промптов

Кэширование промптов — сохранение результата обработки первого запроса для переиспользования в последующих запросах с идентичным контентом.

Механизм: первый запрос → Claude обрабатывает и сохраняет работу в кэш → последующие запросы с тем же контентом → Claude берёт работу из кэша вместо повторной обработки.

Время жизни кэша — максимум 1 час.

Кэширование включается вручную — нужно добавить точку кэширования (cache breakpoint) в блок сообщения.

Форматы текстового блока:

  • Сокращённый: content = "текст" (cache control добавить нельзя)
  • Полный: content = [{"type": "text", "text": "...", "cache_control": {...}}] (нужен для кэширования)

Область кэша — кэшируется весь контент до точки кэширования включительно.

Инвалидация — любое изменение контента до точки кэширования инвалидирует весь кэш.

Порядок обработки контента — tools → system prompt → messages (склеиваются вместе).

Где можно ставить точки кэширования:

  • Схемы инструментов
  • Системные промпты
  • Блоки сообщений (text, image, tool use, tool result)

Максимум точек кэширования — 4 на запрос.

Несколько точек — создают несколько уровней кэша; возможны частичные попадания, если меняется только более поздний контент.

Минимальный порог — контент должен быть не меньше 1024 токенов, чтобы закэшироваться.

Лучшие сценарии — повторяющийся идентичный контент (системные промпты, описания инструментов, неизменные префиксы сообщений).

Кэширование промптов на практике

Реализация кэширования — автоматически кэшировать схемы инструментов и системные промпты, чтобы снизить расход токенов.

Настройка — изменить функцию chat так, чтобы кэширование инструментов и системного промпта было включено по умолчанию.

Кэширование схем инструментов — добавить поле cache_control с типом "ephemeral" к последнему инструменту в списке. Хорошая практика: сделать копию списка, клонировать последнюю схему, добавить cache control и заменить её, чтобы не менять исходные схемы.

Кэширование системного промпта — обернуть его в словарь текстового блока с cache_control типа "ephemeral".

Несколько точек кэширования — можно одновременно кэшировать и инструменты, и системный промпт в одном запросе.

Порядок кэша — tools → system prompt → messages.

Показатели использования токенов:

  • cache_creation_input_tokens — токены, записанные в кэш при первом использовании
  • cache_read_input_tokens — токены, прочитанные из кэша в последующих одинаковых запросах
  • Возможно частичное чтение кэша, когда совпадает только часть контента

Инвалидация — любое изменение закэшированного контента (инструментов или системного промпта) инвалидирует кэш и вызывает создание нового.

Сценарии — одинаковый контент в разных запросах: те же схемы инструментов, системные промпты или последовательности сообщений.

Выполнение кода и Files API

Files API — позволяет загружать файлы заранее и ссылаться на них по file ID вместо передачи сырых данных в каждом запросе. Загрузить файл → получить объект метаданных с ID → использовать ID в следующих запросах.

Code Execution — серверный инструмент, с помощью которого Claude выполняет Python-код в изолированных Docker-контейнерах. Реализовывать ничего не нужно — достаточно подключить готовую схему инструмента. Claude может запускать код многократно, интерпретировать результаты и формировать итоговый ответ.

Ключевые ограничения: у Docker-контейнеров нет доступа к сети. Ввод и вывод данных — только через интеграцию с Files API.

Совместный сценарий: загрузить файл через Files API → получить file ID → указать ID в блоке container upload → попросить Claude проанализировать → Claude пишет и выполняет код с доступом к файлу → возвращает анализ и результаты.

Claude может создавать файлы (графики, отчёты) внутри контейнера, их можно скачать по file ID из ответа.

Сценарии: анализ данных, обработка файлов, автоматическая генерация кода для сложных задач. Ответ содержит блоки кода, результаты выполнения и итоговый анализ.

Реализация: блок container upload с file ID + промпт с задачей анализа — выполнение кода Claude берёт на себя.

Знакомство с MCP

MCP (Model Context Protocol) — коммуникационный слой, дающий Claude контекст и инструменты без необходимости писать много рутинного кода.

Архитектура: MCP-клиент подключается к MCP-серверу. Сервер содержит инструменты (tools), ресурсы (resources) и промпты (prompts).

Какую проблему решает: избавляет от необходимости писать и поддерживать множество схем и функций инструментов для интеграций с сервисами. Например, чат-бот для GitHub потребовал бы инструментов для репозиториев, pull request’ов, issues, проектов — это большой объём работы.

Решение: определением и выполнением инструментов занимается MCP-сервер, а не сервер вашего приложения. MCP-серверы — интерфейсы к внешним сервисам, оборачивающие их функциональность в готовые инструменты.

Главное преимущество: разработчику не нужно самому писать схемы и реализации инструментов.

Частые вопросы:

  • Кто создаёт MCP-серверы? Кто угодно; часто официальные реализации делают сами поставщики сервисов (AWS и др.)
  • Чем отличается от прямых вызовов API? С MCP не нужно самому писать схемы и функции инструментов
  • Чем отличается от tool use? MCP и tool use дополняют друг друга: MCP определяет, КТО выполняет работу (сервер или разработчик), но в обоих случаях используются инструменты

Главная ценность: нагрузка по интеграции переходит с разработчиков приложений на мейнтейнеров MCP-серверов.

MCP-клиенты

MCP-клиент — интерфейс связи между вашим сервером и MCP-сервером, дающий доступ к инструментам сервера.

Независимость от транспорта — клиент и сервер могут общаться по разным протоколам (stdio, HTTP, WebSockets).

Типичная конфигурация — клиент и сервер на одной машине, обмен через стандартный ввод/вывод.

Коммуникация — обмен сообщениями, описанными в спецификации MCP.

Основные типы сообщений:

  • list tools request — клиент запрашивает у сервера список инструментов
  • list tools result — сервер отвечает списком инструментов
  • call tool request — клиент просит сервер выполнить инструмент с аргументами
  • call tool result — сервер возвращает результат выполнения

Типичный поток:

  1. Пользователь отправляет запрос на сервер
  2. Сервер запрашивает список инструментов у MCP-клиента
  3. MCP-клиент отправляет list tools request на MCP-сервер
  4. MCP-сервер отвечает list tools result
  5. Сервер отправляет запрос + инструменты в Claude
  6. Claude запрашивает выполнение инструмента
  7. Сервер просит MCP-клиента выполнить инструмент
  8. MCP-клиент отправляет call tool request на MCP-сервер
  9. MCP-сервер выполняет инструмент (например, вызов GitHub API)
  10. Результаты идут обратно по цепочке: MCP-сервер → MCP-клиент → сервер → Claude → пользователь

Назначение — позволить серверам делегировать выполнение инструментов специализированным MCP-серверам, сохраняя интеграцию с Claude.

Настройка проекта

Компоненты проекта:

  • MCP-сервер — предоставляет 2 инструмента (чтение документа, изменение документа)
  • Коллекция документов — фейковые документы, хранящиеся только в памяти

Важно: в обычных проектах реализуют либо клиент, либо сервер. Здесь — оба, в учебных целях.

Определение инструментов в MCP

Реализация MCP-сервера на Python SDK создаёт инструменты через декораторы, а не через ручные JSON-схемы.

MCP Python SDK — официальный пакет, автоматически генерирующий JSON-схемы инструментов из определений Python-функций с декоратором @mcp.tool.

Синтаксис — @mcp.tool(name="tool_name", description="описание") + функция с типизированными параметрами, описания аргументов задаются через Field().

Реализованные инструменты:

  1. read_doc_contents — принимает строку doc_id, возвращает содержимое документа из словаря docs в памяти
  2. edit_document — принимает doc_id, old_string, new_string и выполняет поиск с заменой в документе

Обработка ошибок — проверить, есть ли doc_id в словаре docs, и выбросить ValueError, если нет.

Главное преимущество — SDK избавляет от ручного написания JSON-схем, генерируя их из сигнатур функций и декораторов.

Необходимые импорты — Field из pydantic для описаний параметров, пакет mcp для сервера и декораторов.

Шаблон — декоратор задаёт метаданные инструмента, параметры функции — аргументы с типами и описаниями, тело функции — логику инструмента.

Инспектор сервера

MCP Inspector — отладчик в браузере для тестирования MCP-серверов без подключения к приложению.

Запуск: выполнить в терминале mcp dev [server_file.py] → сервер стартует на порту → открыть указанный URL в браузере.

Интерфейс: в левой панели — кнопка подключения → в верхнем меню разделы resources / prompts / tools → в разделе tools список инструментов → клик по инструменту открывает правую панель для ручного тестирования.

Порядок тестирования: подключиться к серверу → перейти в tools → выбрать инструмент → ввести параметры → нажать Run Tool → проверить результат.

Ключевые возможности: тестирование в процессе разработки, ручной вызов инструментов, формы ввода параметров, индикация успеха/ошибки, без интеграции с полноценным приложением.

Примечание: интерфейс активно меняется, но базовая функциональность остаётся похожей.

Пример: протестировать инструменты для документов — ввести ID документа, проверить чтение, затем изменение, связать операции, чтобы убедиться, что изменения применились.

Главная польза: эффективная отладка реализации MCP-сервера во время разработки.

Реализация клиента

MCP-клиент — класс-обёртка над client session для очистки ресурсов и управления подключением к MCP-серверу.

Client session — собственно соединение с MCP-сервером из MCP Python SDK; требует освобождения ресурсов при закрытии.

Назначение клиента — открыть функциональность MCP-сервера остальному коду: получать список инструментов и выполнять их.

Ключевые функции:

  • list_tools() — await self.session.list_tools(), вернуть result.tools
  • call_tool() — await self.session.call_tool(tool_name, tool_input)

Порядок использования — клиент получает определения инструментов для передачи в Claude, а затем выполняет их по запросу Claude.

Частый шаблон — оборачивать client session в более крупный класс для управления ресурсами, а не использовать сессию напрямую.

Тестирование — файл клиента можно запустить напрямую с тестовой обвязкой, чтобы проверить подключение к серверу и получение инструментов.

Интеграция — остальной код проекта вызывает функции клиента для работы с MCP-сервером, что позволяет Claude читать и редактировать документы через определённые инструменты.

Определение ресурсов

MCP Resources — механизм, позволяющий MCP-серверам отдавать клиентам данные для чтения.

Типы ресурсов — 2 типа: прямые (статический URI, например docs://documents) и шаблонные (URI с параметрами, например docs://documents/{doc_id}).

URI — адрес/идентификатор для доступа к конкретному ресурсу, задаётся при создании ресурса.

Поток: клиент отправляет read resource request с URI → сервер сопоставляет URI с функцией → выполняет её → возвращает данные в read resource result.

Реализация — декоратор @mcp.resource с параметрами URI и MIME-типа.

MIME-типы — подсказка клиенту о формате данных (application/json для структурированных данных, text/plain для обычного текста).

Шаблонные ресурсы — параметры URI автоматически парсятся SDK и передаются в функцию-обработчик как именованные аргументы.

Ресурсы и инструменты — ресурсы отдают данные проактивно (например, содержимое документа при @-упоминании), инструменты выполняют действия реактивно (когда Claude решает их вызвать).

Возврат данных — SDK автоматически сериализует данные в строки, десериализация — на стороне клиента.

Тестирование — MCP Inspector показывает прямые и шаблонные ресурсы отдельно и позволяет проверить отдельные вызовы.

Доступ к ресурсам

Функция чтения ресурса — клиентская функция для запроса и парсинга ресурсов с MCP-сервера.

Параметры функции — URI (идентификатор ресурса).

Шаги реализации:

  • Импортировать модуль json и AnyUrl из pydantic
  • Вызвать await self.session.read_resource(AnyUrl(uri))
  • Взять первый элемент result.contents[0]
  • Проверить resource.mime_type, чтобы выбрать способ парсинга

Логика парсинга:

  • Если mime_type == "application/json" → вернуть json.loads(resource.text)
  • Иначе → вернуть resource.text (обычный текст)

Структура ответа сервера — список result.contents, первый элемент которого содержит метаданные типа и mime_type.

Интеграция — функции MCP-клиента вызываются другими компонентами приложения, чтобы получить содержимое документов для промптов.

Итог — содержимое документов автоматически попадает в промпт Claude без вызова инструментов.

Главное — ресурсы напрямую открывают данные сервера клиентам по структурированной схеме запрос/ответ.

Определение промптов

MCP Prompts — заранее подготовленные и протестированные шаблоны промптов, которые MCP-сервер предоставляет клиентским приложениям для специализированных задач.

Назначение — вместо того чтобы пользователи писали промпты наугад, авторы сервера создают качественные, проверенные промпты под предметную область своего сервера.

Реализация — декоратор @mcp.prompt с именем и описанием + функция, возвращающая список сообщений (user/assistant), которые можно сразу отправить в Claude.

Пример — промпт форматирования документа: принимает ID документа, поручает Claude прочитать его через инструменты, переформатировать в markdown и сохранить изменения.

Преимущества — экспертиза под конкретный сервер, проверенное качество, переиспользование в разных клиентах, результаты лучше, чем у промптов, написанных пользователем.

Структура сообщений — возвращаются объекты base.UserMessage с текстом промпта и подставленными параметрами.

Интеграция с клиентом — промпты появляются как варианты автодополнения (слэш-команды), клиент запрашивает у пользователя нужные параметры и запускает готовый сценарий.

Промпты в клиенте

Работа с промптами в MCP-клиенте:

  • Список промптов — await self.session.list_prompts(), вернуть result.prompts
  • Получить промпт — await self.session.get_prompt(prompt_name, arguments), вернуть result.messages

Порядок работы:

  1. Определить промпт на MCP-сервере с ожидаемыми аргументами (например, document_id)
  2. Клиент вызывает get_prompt с именем промпта и словарём аргументов
  3. Аргументы передаются в функцию промпта как именованные
  4. Функция подставляет аргументы в текст промпта
  5. Возвращается массив сообщений для прямой передачи в LLM

Суть: промпты — это шаблоны на стороне сервера, которые клиент вызывает с конкретными аргументами, получая инструкции с контекстом для LLM. Аргументы проходят путь: вызов клиента → функция промпта → текст с подстановкой → LLM.

Приложения Anthropic

Приложения Anthropic — два готовых продукта: Claude Code и Computer Use.

Claude Code — терминальный помощник по программированию, служащий примером архитектуры агента.

Computer Use — набор инструментов, расширяющий возможности Claude за пределы генерации текста.

Назначение — эти приложения демонстрируют концепции агентов и служат практическими примерами для понимания их проектирования и реализации.

Настройка — включает конфигурацию терминала для работы с Claude Code на учебных проектах.

Связь с агентами — оба приложения показывают, как работают агенты, и служат моделью для создания эффективных агентов.

Настройка Claude Code

Claude Code — терминальная программа-помощник для задач, связанных с кодом.

Базовые возможности — поиск/чтение/редактирование файлов + продвинутые инструменты (загрузка веб-страниц, доступ к терминалу) + поддержка MCP-клиента для расширения функциональности через MCP-серверы.

Установка:

  1. Установить Node.js (проверить командой npm help)
  2. Установить Claude Code через npm install
  3. Запустить команду claude в терминале и войти в аккаунт Anthropic

Полное руководство — docs.anthropic.com.

Функции MCP-клиента — может использовать инструменты MCP-серверов, расширяя возможности за пределы базовых операций с файлами.

Claude Code в деле

Claude Code — ИИ-помощник, работающий как полноценный инженер-партнёр в проекте, а не просто генератор кода.

Ключевые возможности: настройка проекта, проектирование фич, написание кода, тестирование, деплой, исправление ошибок в продакшене.

Порядок начала работы:

  • Скачать проект, открыть в редакторе
  • Запустить команду claude
  • Попросить Claude прочитать README и выполнить инструкции по настройке
  • Выполнить команду init — Claude просканирует кодовую базу (архитектуру, стиль кода) и создаст файл claude.md
  • claude.md — контекст, который автоматически включается в последующие запросы

Типы памяти: проектная (общая), локальная, пользовательская.

Управление контекстом:

  • Символ # позволяет добавить в память конкретные заметки
  • Можно вручную редактировать claude.md или заново запустить init
  • Claude умеет выполнять операции Git (staging, commit)

Эффективные стратегии промптинга:

Метод 1 — три шага:

  1. Определить релевантные файлы и попросить Claude их проанализировать
  2. Описать фичу и попросить Claude спланировать решение (без кода)
  3. Попросить Claude реализовать план

Метод 2 — разработка через тестирование (TDD):

  1. Дать релевантный контекст
  2. Попросить Claude предложить тесты для фичи
  3. Выбрать и реализовать нужные тесты
  4. Попросить Claude писать код, пока тесты не пройдут

Главный принцип: Claude Code — множитель усилий. Чем детальнее инструкции, тем значительно лучше результат. Относитесь к нему как к инженеру-партнёру, а не просто генератору кода.

Расширение через MCP-серверы

В Claude Code встроен MCP-клиент, который может подключаться к MCP-серверам для расширения функциональности.

Подключение MCP-сервера — внешние инструменты и сервисы подключаются командой claude mcp add [имя-сервера] [команда-запуска].

Пример — сервер обработки документов с инструментом «Document Path to Markdown», позволяющий Claude Code читать PDF/Word-документы; запускается через uv run main.py.

Динамическое расширение — MCP-серверы добавляют Claude Code новые функции на лету, без изменения ядра.

Частые сценарии — мониторинг продакшена (Sentry), управление проектами (Jira), коммуникации (Slack), собственные инструменты для процесса разработки.

Главная польза — значительно больше гибкости в процессах разработки благодаря модульным подключениям серверов.

Порядок: 1) создать MCP-сервер с инструментами, 2) добавить сервер в Claude Code с именем и командой запуска, 3) перезапустить Claude Code, чтобы получить новые возможности.

Параллельная работа Claude Code

Распараллеливание Claude Code — одновременный запуск нескольких экземпляров Claude для параллельного выполнения разных задач.

Ключевая проблема — несколько экземпляров, одновременно меняющих одни и те же файлы, создают конфликты и ломают код.

Решение — Git worktrees, дающие каждому экземпляру Claude изолированное рабочее пространство.

Git worktrees — функция Git, создающая полные копии проекта в отдельных директориях, каждая из которых соответствует своей ветке.

Процесс: создать worktree → поручить задачу экземпляру Claude → работа в изоляции → коммит изменений → слияние в основную ветку.

Пользовательские команды — автоматизация создания и управления worktree через директорию .claude/commands с markdown-файлами промптов.

Структура команды — .claude/commands/filename.md с плейсхолдером $ARGUMENTS для динамических значений.

Преимущества — один разработчик управляет «виртуальной командой» инженеров; производительность масштабируется, ограничиваясь лишь способностью разработчика управлять задачами.

Конфликты слияния — Claude автоматически разрешает конфликты при слиянии веток.

Очистка — Claude сам удаляет worktree после завершения фичи.

Главное преимущество — масштабирование до любого числа параллельных экземпляров в пределах возможностей разработчика ими управлять.

Автоматическая отладка

Автоматическая отладка — использование ИИ (Claude) для автоматического обнаружения, анализа и исправления ошибок в продакшене без ручного вмешательства.

Основной процесс:

  1. GitHub Action ежедневно проверяет продакшен-окружение
  2. Забирает логи CloudWatch за последние 24 часа
  3. Claude находит ошибки и убирает дубликаты
  4. Claude анализирует каждую ошибку и генерирует исправления
  5. Создаётся pull request с предлагаемыми решениями

Ключевые компоненты:

  • GitHub Actions — расписание и автоматизация
  • AWS CLI — получение логов
  • Claude Code — анализ ошибок и исправление кода
  • CloudWatch — мониторинг ошибок в продакшене

Преимущества:

  • Ловит ошибки, проявляющиеся только в продакшене
  • Сокращает время ручного поиска по логам и отладки
  • Даёт исправления с учётом контекста и пояснениями
  • Создаёт pull request’ы, которые можно проверить

Частый случай: ошибки конфигурации между окружениями (неверные ID моделей, API-ключи и т. п., которые работают локально, но падают в продакшене).

Что нужно: доступ к репозиторию, сервис логирования в облаке, ИИ-помощник по коду, интеграция с CI/CD.

Computer Use

Computer Use — способность Claude взаимодействовать с интерфейсами компьютера через визуальное наблюдение и управляющие действия.

Ключевые возможности:

  • Делает скриншоты приложений и браузеров
  • Нажимает кнопки, вводит текст, перемещается по интерфейсу
  • Самостоятельно выполняет многошаговые инструкции
  • Выполняет QA-тестирование и задачи автоматизации

Как работает:

  • Запускается в изолированном Docker-контейнере
  • Пользователь даёт инструкции через чат
  • Claude визуально наблюдает экран и выполняет действия
  • Формирует отчёты о выполнении и результатах

Основные сценарии:

  • Автоматическое QA-тестирование веб-приложений
  • Тестирование взаимодействия с UI в разных сценариях
  • Экономия времени на повторяющихся задачах за компьютером
  • Поиск багов через систематическое тестирование

Для локального тестирования доступна эталонная реализация.

Пример: пользователь описывает требования к тестированию → Claude открывает приложение → выполняет тест-кейсы → сообщает pass/fail с подробными выводами.

Как работает Computer Use

Computer Use — реализация на основе системы инструментов, позволяющая Claude взаимодействовать с вычислительным окружением.

Обычный tool use: пользователь отправляет сообщение + схему инструмента → Claude отвечает запросом tool use (ID, имя, вход) → сервер выполняет код → результат отправляется в Claude как tool result.

Computer Use работает точно так же:

  • В Claude отправляется специальная схема инструмента (маленькая схема за кулисами разворачивается в большую)
  • Развёрнутая схема содержит функцию action с аргументами: перемещение мыши, левый клик, скриншот и т. д.
  • Claude присылает запрос tool use
  • Разработчик выполняет его в вычислительном окружении (обычно Docker-контейнер)
  • Контейнер программно нажимает клавиши и двигает мышь
  • Ответ отправляется обратно в Claude

Ключевые моменты:

  • Claude не управляет компьютером напрямую
  • Computer Use = система инструментов + окружение, предоставленное разработчиком
  • Anthropic предоставляет эталонную реализацию (Docker-контейнер с готовым кодом управления мышью и клавиатурой)
  • Для запуска нужен Docker и одна простая команда
  • Есть чат-интерфейс для прямого тестирования Computer Use

Computer Use — слой абстракции: система инструментов отвечает за общение с Claude, а Docker-контейнер — за реальные действия на компьютере.

Агенты и воркфлоу

Воркфлоу и агенты — стратегии для задач, которые Claude не может выполнить за один запрос.

Правило выбора: воркфлоу — когда задача хорошо понятна и известна точная последовательность шагов. Агенты — когда детали задачи неясны.

Воркфлоу — серия вызовов Claude для конкретной задачи с заранее определёнными шагами.

Пример воркфлоу — конвертер изображения в 3D-модель:

  • Шаг 1: Claude подробно описывает загруженное изображение
  • Шаг 2: Claude моделирует объект по описанию с помощью Python-библиотеки CadQuery
  • Шаг 3: создаётся рендер модели
  • Шаг 4: Claude сравнивает рендер с исходным изображением
  • Шаг 5: если неточно — повтор с шага 2 с обратной связью

Это паттерн evaluator-optimizer:

  • Producer — создаёт результат (Claude + моделирование в CadQuery)
  • Evaluator — оценивает качество (шаг сравнения)
  • Цикл продолжается, пока evaluator не примет результат

Важно: воркфлоу — это паттерны реализации, которые успешно применяли другие инженеры. Узнать паттерн — не значит его реализовать: код всё равно нужно писать.

Воркфлоу распараллеливания

Распараллеливание — разбиение одной сложной задачи на несколько одновременных подзадач с последующим объединением результатов.

Пример — выбор материала для детали:

  • Вместо: один большой промпт, где Claude выбирает между металлом/полимером/керамикой/композитом по всем критериям
  • Лучше: отдельные параллельные запросы, каждый оценивает пригодность одного материала, затем шаг агрегации сравнивает результаты

Структура: вход → несколько параллельных подзадач → агрегатор → итоговый результат.

Преимущества:

  • Фокус — каждая подзадача решает один конкретный анализ, а не жонглирует множеством соображений
  • Модульность — отдельные промпты можно улучшать и оценивать независимо
  • Масштабируемость — легко добавить подзадачу, не затрагивая остальные
  • Качество — меньше путаницы, чем в перегруженном едином промпте

Ключевой принцип: разложить сложное решение на специализированные параллельные анализы, затем синтезировать результаты.

Воркфлоу-цепочки

Цепочка (chaining) — разбиение большой задачи на серию отдельных последовательных шагов вместо одного сложного промпта.

Основная идея: вместо одного огромного промпта с множеством требований — отдельные вызовы, каждый сосредоточен на одной подзадаче.

Пример: пользователь вводит тему → поиск трендовых тем → Claude выбирает самую интересную → Claude исследует тему → Claude пишет сценарий → генерация видео → публикация в соцсетях.

Главная польза: ИИ фокусируется на отдельных задачах, а не держит в голове много ограничений одновременно.

Основной сценарий: когда Claude стабильно игнорирует ограничения в сложном промпте, даже если их повторять. Часто бывает с длинными промптами со множеством требований «не делай X».

Проблемная ситуация: длинный промпт с ограничениями (не упоминать ИИ, без эмодзи, профессиональный тон) → Claude нарушает часть из них, сколько ни повторяй.

Решение: шаг 1 — отправить исходный промпт и принять неидеальный результат. Шаг 2 — дополнительным промптом попросить Claude переписать текст с учётом найденных нарушений.

Ключевой вывод: даже простой на вид воркфлоу становится необходимым, когда промпт перегружен ограничениями, которые ИИ не может выполнить за один проход.

Воркфлоу маршрутизации

Маршрутизация (routing) — паттерн, который классифицирует ввод пользователя, чтобы выбрать подходящий пайплайн обработки.

Механизм: первый запрос к Claude относит ввод к одной из заранее определённых категорий. По результату система направляет запрос в специализированный пайплайн со своими промптами и инструментами.

Пример:

  1. Пользователь вводит тему (например, «функции в Python»)
  2. Claude определяет категорию («обучающая»)
  3. Система берёт шаблон промпта для обучающего контента
  4. Claude пишет сценарий в обучающем тоне и структуре

Преимущества: результат соответствует характеру темы. Темы о программировании получают обучающую подачу с определениями и объяснениями, развлекательные — трендовый язык и цепляющие хуки.

Структура: один шаг маршрутизации → несколько специализированных пайплайнов → у каждого свои промпты и инструменты под категорию.

Сценарий: генерация сценариев видео для соцсетей, где разные темы требуют разного тона и подхода.

Агенты и инструменты

Агенты — ИИ-системы, которые сами составляют план выполнения задачи с помощью предоставленных инструментов; эффективны, когда точные шаги неизвестны. Воркфлоу лучше, когда шаги известны.

Ключевое отличие: воркфлоу требуют заранее определённых шагов, агенты планируют динамически с помощью доступных инструментов.

Преимущества агентов: гибкость — один набор инструментов решает разные задачи; инструменты можно комбинировать неожиданными способами.

Принцип абстракции инструментов: давайте общие, абстрактные инструменты, а не узкоспециализированные. Пример — Claude Code использует bash, web_fetch, file_write (абстрактные), а не refactor_tool, install_dependencies (специализированные).

Пример комбинирования: get_current_datetime + add_duration + set_reminder в разных комбинациях решают разные задачи, связанные со временем.

Поведение агента: может запросить дополнительную информацию, творчески комбинирует инструменты для достижения цели, лучше всего работает с небольшим набором гибких инструментов.

Подход к проектированию: давать агенту абстрактные инструменты, которые можно собирать вместе, а не одноцелевые специализированные. Это позволяет решать задачи динамически и находить неожиданные применения.

Инспекция окружения

Инспекция окружения — оценка агентом своего окружения и результатов действий, чтобы понимать прогресс и обрабатывать ошибки.

Основная идея: после каждого действия агенту нужна обратная связь помимо простого ответа инструмента, чтобы понять новое состояние окружения.

Пример с Computer Use: Claude делает скриншот после каждого действия (ввод текста, клик), чтобы увидеть, как изменилось окружение, — он не может заранее знать точный результат нажатия кнопки.

Пример с редактированием кода: прежде чем менять файл, агент должен прочитать его текущее содержимое.

Применение в агенте для видео в соцсетях:

  • Использовать Whisper.cpp через bash для генерации субтитров с таймкодами и проверки расстановки реплик
  • Использовать FFmpeg для извлечения кадров видео через интервалы и визуальной проверки
  • Проверять, что созданное видео соответствует ожиданиям, перед публикацией

Главная польза: инспекция окружения позволяет агенту оценивать прогресс, находить ошибки и адаптироваться к неожиданным результатам, а не действовать вслепую.

Воркфлоу против агентов

Воркфлоу — заранее определённая серия вызовов Claude с известными шагами. Агенты — гибкий подход: Claude сам комбинирует базовые инструменты для решения неизвестных заранее задач.

Ключевые различия:

  • Разбиение задач: воркфлоу делят большие задачи на мелкие конкретные подзадачи, что повышает фокус и точность. Агенты творчески справляются с разнообразными задачами без заданных шагов.
  • Тестирование и оценка: воркфлоу легче тестировать — последовательность выполнения известна. Агентов тестировать сложнее — путь выполнения непредсказуем.
  • Пользовательский опыт: воркфлоу требуют конкретных входных данных. Агенты сами формируют входы из запроса пользователя и могут запросить дополнительные данные.
  • Успешность: у воркфлоу выше доля успешно выполненных задач благодаря структуре. У агентов ниже — из-за делегированной сложности.

Рекомендация: в приоритете воркфлоу ради надёжности. Агенты — только когда действительно нужна гибкость. Пользователям нужен продукт, который работает на 100%, а не модный агент.

Главный принцип: сначала надёжно решить задачу, инновации — потом.
